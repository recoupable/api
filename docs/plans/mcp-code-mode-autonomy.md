# Operating a label through Recoup

**Proposed first-release contract.** A company can appoint an agent to perform work that its authorized staff can perform. The first action slice must persist a real change without per-action confirmation. The unattended label release must complete a job after the initiating chat closes, even when the optional standing-instruction and approval modules are absent. Track product capability parity by business outcome, including the source of authority, supported entry points, downstream requirements and evidence of completion for each operation.

## Who decides and who acts

| Component | Responsibility |
| --- | --- |
| Company identity and delegation | An authorized company administrator appoints a separately identifiable agent, selects its company and delegates either the full company operating role or specified operations and resources. The owner can attach destination, spending or time limits when desired. A background worker authenticates as that agent with a renewable, audience-bound credential. Renewal respects the original grant's expiry and revocation. Existing personal registration issues one hour of personal `mcp:read` access and has no refresh token. Company appointment and worker credential renewal are new implementation work. [Current personal registration](../agent-registration.md) |
| Agent and optional standing instructions | An authorized caller can assign a goal directly. A company may also save a recurring instruction describing the trigger, selection criteria and desired outcome. The agent chooses the operations, checks the results and decides how to proceed within its delegation. Instruction text, tool input and stored case assertions cannot mint credentials or enlarge the company's grant. |
| API authorization | The API resolves the actual principal, delegation and current resource permissions. For a concrete action it returns **allow**, **deny**, or **requires interaction** with a reason and, where available, a supported next action. A valid company delegation that covers the action is sufficient for unattended dispatch. An organization may configure additional approvals for particular work. A qualifying individual approval can satisfy that condition within the approver's own authority. Enforce genuine host or provider requirements at the boundary that owns them. |
| Operation owner and workflow | The operation owner checks business preconditions, reserves shared budget atomically when applicable and issues an idempotent request. A durable Recoup workflow records the goal, actor, business key, source versions, checkpoints and completion criteria. It rechecks live authority before each effect and before exposing saved results. It resumes across worker replacement and reconciles an uncertain dispatch against its original receipt. |

The direct MCP exposes `search` and `execute`. A program inside `execute` reads with `recoup.read(id, args)` and requests an effect with `recoup.act(id, args, {requestKey})`. The outer program and each effect have separate stable request keys. For **allow**, the broker dispatches the effect immediately inside `execute` and records the receipt or job handle. For **deny**, it stops before dispatch. When policy requires approval, it parks the exact intent and returns `approval_required`. The optional third MCP tool, `commit({intent, requestKey})`, applies only the parked effect after the approval is independently recorded and current authority passes again. The rest of the run can then continue from its checkpoint with `execute({runId, resume:true})`. Status lookup by `runId` or the outer `requestKey` has no business effect. A provider-owned signature or approval step can remain pending in the underlying job even after dispatch.

The principal or authorized policy owner controls delegation. A guest program cannot select its authority, claim that a person approved, or raise its budget. A run whose authorization expires while queued must be denied before the effect.

For example, an owner can say “check the release catalog today and open cases for confirmed missing identifiers.” The same owner can save “do this every Monday and reopen a case only when the evidence changes.” A scheduler submits the same job under the same company agent. If the owner later chooses “ask me before sending a correction outside the label,” that exact send pauses when a qualified sending operation exists. The agent can keep handling unrelated private cases. Removing the recurring assignment stops its future triggers and leaves the underlying grant under the owner’s control.

REST, standard named MCP tools, direct code mode and the first-party app call the same operation and authorization logic. Verify equivalent outcomes for equivalent principals, capabilities and resources. Different audiences may have different entitlements. Preserve legacy grants without upgrading them. The Directory exposes only its individually reviewed actions. A Directory consent dialog or downstream requirement for a person's signature applies to that channel or transaction. An unattended job needing that step records the dependency, waits or routes an exception, then resumes using the original intent. Keep a capability ledger for human-supported jobs that still lack a delegated API action, provider access, readback or distribution path.

## First job and its implementation gap

For a disposable label, assign an agent to open one private metadata correction case per recording with current evidence of a missing recording identifier (ISRC). Appoint the agent with full operating authority over the disposable label and give it this one-off task with no stored instruction or action-specific approval. Only the private case change is needed. Repeat under a narrower delegation limited to catalog reads and case edits, with zero spend and external messaging disabled. These are two configurations of the same interface. A company can later schedule the assignment as a standing instruction.

Existing code distinguishes an observed missing ISRC from a failed lookup, partial coverage and stale source versions. `POST /api/context` and standard MCP already save and reopen workspace-scoped catalog cases with revision checks and idempotency keys. Saved cases are private workpapers. A stored assertion about authorization confers no provider authority. The existing delegated MCP profile excludes case save, read and list. Add the case operations to the full company role and make the same operations individually selectable for a restricted role. Verify the workspace and evidence boundaries before offering the job in direct code mode. Reuse the existing case processor, validate evidence against the selected recording and workspace, and keep withdrawal/redaction behavior on subsequent reads. ## Installed end-to-end acceptance

1. Seed two isolated organizations. Give the pilot label multiple pages of releases, known missing ISRCs, a failed lookup, a conflict, an already-handled recording and a partial source. Define the expected outcomes independently of the agent. Have an authorized administrator create the grant once. Run the same business operation through REST and the direct MCP host using equivalent isolated fixtures. On the direct path the agent uses `recoup.act` in `execute`, and the receipt must identify an immediate delegated dispatch with zero `commit` calls. Use standard named MCP as an additional control where its existing credential is eligible.
2. Start the agent's job and end its initiating session. Restart a worker, run a second worker against the same business key and change a source version during execution. Persist a stable key derived from organization, recording and correction kind across sessions. Use the existing case ID for retries, check the expected revision and keep source versions on the case so later evidence can update it. Record an unresolved finding when the evidence cannot support a confirmed gap.
3. Using an independent authorized read path, reopen each saved case and verify its ID, workspace, recording, revision, evidence references and source freshness against the seed. Confirm zero wrong or duplicate cases and no cross-company case access, messages, spending or rights changes. Revoke the delegation while a second job is queued and verify zero subsequent writes. For the optional approvals release, configure a separate trial to require one approval. Verify that the exact effect stays parked, the optional `commit` applies it once after approval, and resuming the checkpoint preserves earlier completed effects.
4. Publish a redacted receipt with expected versus observed cases, reason for every unresolved recording, number of human interruptions **after appointment**, recovery behavior and cost per verified case. An accepted job or an in-memory preview is insufficient. The release gate is a persisted business change with independent readback and unattended completion under the original company delegation.
