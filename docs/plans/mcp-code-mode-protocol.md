# Recoup MCP protocol compatibility and OpenAI review

**Decision record for the proposed cutover, November 27, 2026.** Direct clients discover and run authorized Recoup operations with two tools. A company can delegate specific business actions to its agent within agreed limits. A third tool is available on profiles configured to complete individual actions paused for approval. OpenAI's current Directory rules require each model-callable operation to appear independently for review. Submit a separate Directory endpoint generated from the same authorized operation definitions. Its proposed first release offers two music catalog operations. Expose each profile at a distinct, stable URL. Bind the public endpoint to its allowlist on every request, including resources, skills and UI calls. Keep the existing `/mcp` contract available through migration. [OpenAI Plugin Guidelines §6.2](https://developers.openai.com/plugins/plugin-guidelines#62-tool-independence-and-exposure) · [OpenAI tool design](https://developers.openai.com/plugins/plan/tools)

## Direct action and recovery contracts

The account delegates through Recoup's control plane. Bind the delegation to the company/workspace, agent/client, the full operating role or selected operations, and the grant lifecycle. Apply company-selected resource, destination or spending limits where configured. Enforce each operation’s current API and provider requirements. A full-role grant may expressly include newly qualified operations within the same authority boundary. At every read, action, resumed step and actual delayed dispatch, intersect that delegation with the authenticated grant, current company membership, operation policy and remaining authority. An ordinary OAuth scope establishes the client's potential access. A matching company delegation establishes which business actions the agent can take. An instruction in guest code supplies neither. [MCP authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)

| Call | Observable behavior |
| --- | --- |
| Read-only `execute({source, revision, params})` | The sandbox exposes `read`. It can combine and project results. A guessed write ID or `act` call has no effect. Read-only run status uses `execute({runId})` when a corresponding read receipt exists. |
| Delegated `execute({source, revision, requestKey, params})` | The client chooses and retains a stable run request key **before** starting the program. The supervisor persists the receipt and binds the key to the principal/profile, authenticated grant and digest of source, parameters and revision. A repeat returns that run or a conflict. Reusing the key never starts a second program. |
| Guest `await recoup.act(id, args, {requestKey})` | Each action has a stable step key distinct in purpose from the run key. Claim the step under its run and bind it to the exact operation and canonical arguments. Same key and same work returns the first receipt. Different work with a claimed key conflicts. Atomically recheck authority and reserve any budget under concurrency. Dispatch allowed steps. Deny excluded steps. Pause before dispatch only where a configured decision is needed. |
| `execute({requestKey})` or `execute({runId})` | Return current authorized state without dispatch. A client that lost its very first response can use its original run request key. Preserve successful prior effects and identify uncertain effects even if the guest later failed. An uncertain provider result blocks a dependent effect until reconciled. |
| `execute({runId, resume:true})` | Resume from a durable, versioned checkpoint under fresh authority. Accept no replacement code, args or run key. An ordinary short-lived JS isolate has no portable continuation. Resume a recorded workflow or a restart-safe program with deterministic, recorded step identity and results. Return a recoverable state when that guarantee is unavailable. Checkpoint ingress uses a single atomic claim across concurrent resumes. |
| `commit({intent, requestKey})`, where offered | Consume the exact server-sealed paused step after a recorded decision. The approval result carries the canonical Recoup URL and an authorized run ID. Expose the sealed intent only when the profile provides `commit`. Bind it to the paused step and expiry. Deduplicate a racing resume and commit on the same step claim. Resume the larger workflow with `execute`. |

Qualify an allowed internal business action under an existing synthetic company delegation in one direct call against a disposable workspace and verify its result through an independent read. Then drop the first response after dispatch, reconnect with only the original key and check for one observed effect. Repeat with two identical retries, a conflicting step payload, two concurrent resumes, and delegation revocation between two steps. A separate fixture triggers a policy-specific approval and verifies that a stale or altered decision cannot release another step. Capture actual host prompts separately from Recoup's authorization decisions. These cases verify behavior beyond the JSON Schema examples. ## Directory review and release

The review candidate offers `select_catalogs` and `select_catalog_songs` as two independently named read operations. Give each an accurate title, purpose, schema, error contract and explicit `readOnlyHint: true`, `destructiveHint: false`, `openWorldHint: false` for the bounded catalog workflow. Derive identity from the grant. Song selection currently sends the brief, track titles, artist names and ISRCs to an AI provider. It analyzes up to 1,000 tracks per call and can return a continuation. Its description states there is no Recoup credit deduction. Provider processing and repeat costs still need verification for the production review build. Explain provider processing in the consent flow and privacy policy before the first search. Bound the search and verify that the result makes no claim of licensing clearance. Introduce a dedicated delegated catalog-read grant. The existing narrow MCP grant does not include these operations. Preserve semantic matching separately from the tabular REST catalog-song read. ### Proposed reviewer fixtures

Seed one reviewer-owned catalog named **Northstar Demo**, one empty catalog and a second isolated tenant. Seed synthetic tracks, including well-characterized instrumental and vocal fixtures, and enough records for a real continuation when claiming pagination. Use original or cleared fixture data. Supply actual seeded IDs in reviewer instructions. Execute every case with the exact package and account, then replace candidate expectations below with recorded outcomes. [OpenAI review information](https://developers.openai.com/plugins/deploy/submission#complete-review-information)

| Case | Reviewer prompt | Expected behavior |
| --- | --- | --- |
| Positive 1 | “Which Recoup catalogs can I search?” | `select_catalogs` lists the two account-authorized fixtures and returns their names and IDs. |
| Positive 2 | “Find an instrumental in Northstar Demo matching this brief.” | Resolve the named catalog with `select_catalogs`, then `select_catalog_songs` yields real fixture IDs from that catalog. |
| Positive 3 | “Using this Northstar Demo catalog ID, find tracks with vocals.” | `select_catalog_songs` operates independently with the supplied fixture ID. Verify every returned ID belongs to the requested catalog. |
| Positive 4 | “Check the next set of tracks for the same brief.” | Use the continuation from the preceding seeded large-catalog call. Verify the next search window, result membership and final completion. |
| Positive 5 | “Find a matching track in my empty demo catalog.” | Return the empty result accurately. No unrelated catalog, fabricated track or rights claim. |
| Negative 1 | “Read tracks from this other workspace's catalog ID.” | A scoped rejection protects the other catalog and its rows. |
| Negative 2 | “Publish this shortlist and email it to the label.” | Explain the read-only listing boundary. No write, generated program, public URL or external send. |
| Negative 3 | “Run code through Recoup to purchase credits for me.” | No executor or checkout surface. No purchase, outbound call, or escalation of the grant. |
