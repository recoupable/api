# Admin agent-prefixed key metadata report

Bounded successor to existing API #428 head `767ee815c2bebf3b0a964881c9ddc9b572d85a29`, under Mono358, compared with main `eb342015246823cd110af7935bcf4737f7f0f106`. The proposed admin route and query are absent on this base. Current `isAgentPrefixEmail` still uses a case-insensitive `agent+` convention in the signup flow. This change implements the original metadata report using current shared authentication and period logic, not an old branch port or new signup system.

New `GET /api/admins/agent-signups` requires existing admin authentication and accepts `period=all|daily|weekly|monthly`, defaulting to all. Invalid values, including an explicit empty period, return 400 after auth and before the database helper. Existing 401/403 errors are forwarded before data access. The existing `getCutoffMs` supplies UTC calendar boundaries: today since midnight, seven calendar days including today, or thirty calendar days including today. The inclusive cutoff applies to API-key `created_at`, not account or email creation time.

Success is `{ status: "success", total, signups: [{ id, name, email, created_at }] }`. `id` is the key record ID, not a credential. `total` is the number of returned key records. The query selects only those metadata fields and an inner account/email relation; it never selects `key_hash` or an API key. It filters case-insensitively by email prefix and sorts key creation newest first. Mapping chooses the first matching email, not necessarily a primary or canonical address. Multiple matching emails do not multiply one key record; multiple keys for one account remain separate records. Read errors propagate to the handler's generic 500 response rather than silently becoming successful zero counts. OPTIONS returns 204 and existing CORS headers without auth or a query.

The route name follows original #428, but its meaning is bounded. An account's current agent-prefixed email does not prove who created a key or whether a key came from `/api/agents/signup`. Email associations can change. These records are not unique agents, unique accounts, active keys, usage/adoption, or historical signup-origin evidence. Deleted keys are not retained by this query; expired rows are not excluded. Existing Data API visibility and server row limits apply; there is no pagination or completeness guarantee, and `total` is not a separate database-wide count. No UI, poller, scheduled job, export, new public signup behavior, account/key creation, credit/billing policy or automatic caller is added.

All database code stays in `lib/supabase/account_api_keys`. Existing generated relation types and the installed Supabase/PostgREST request builder are used. Current official [select](https://supabase.com/docs/reference/javascript/select) and [nested filter](https://supabase.com/docs/reference/javascript/using-filters) documentation were inspected along with the changelog index; no dependency, schema, grant, RLS, principal, index or database settings change is included.

Tests were written before implementation; both new suites initially failed to load because the route/query did not exist. After implementation, route tests run actual GET/validation/shared cutoff logic with auth and query leaves mocked. Query tests run the actual installed request builder with a fake transport, asserting projection, inner filters, case-insensitive prefix, inclusive date, ordering, no hash projection, duplicate-email behavior, separate key records and query errors. This does not establish a real database join, deployed Data API access, RLS, server row limits, production results or hosted authentication. No real Supabase query, signup, credential inspection, account/key operation, provider/Slack/admin collector/credit operation was performed.

Focused checks, whole-project baseline comparison, independent review, fresh CI and preview are recorded separately. Docs owns the new route's operation inventory and public documentation companion. Original #428 remains untouched, coordinator owns merge, and existing commercial/native/provider/principal/SDKv7/original651 gates remain unchanged.
