# Editorial images in existing content callbacks

Bounded successor to API #438 head `7db69439a12c817dfb5c97d349f8cc26581b46f6`, under Mono358, compared with API main `8ec416923fc8139556bdb5ebd97f2b73d4663f94`. The recorded criterion adds optional `imageUrl` and delivers the existing editorial image before videos, falling back to its URL on failure. Current callback validation strips that unknown field, and the existing result poster only handles video.

The existing worker already returns the selected/generated base image as `imageUrl`; its polling mapper discards it before callback serialization. The companion Tasks change preserves that field in the existing mapper. This is not a new Trigger job, generation step, image model, paid call, task payload, retry/concurrency/poll-interval change, audio/lipsync change or SDK version upgrade. The installed4.3.3 package maps root and /v3 imports to the same implementation; the modified mapper uses the canonical root import. Existing callback transport/secret behavior is unchanged. API receiver and worker companion are both needed for the normal pipeline to deliver the image.

The API result schema retains optional string `imageUrl`, matching existing videoUrl string validation. Only completed results already selected for having a video are posted; no image-only job, still-only success or new callback status is introduced. Per-result association is preserved, all editorial images are posted in result order before all videos in result order, and the existing caption, video labels, failed-run summary and terminal-thread retry skip remain. Results without images perform no extra image read or post.

A shared downloader retains the existing video Buffer/null behavior while also exposing the media server's normalized reported Content-Type. Image files are attached for image/png, image/jpeg, image/webp and image/gif using that MIME type and an image-specific fallback filename. Failed downloads and missing/unsupported MIME values produce an editorial-image URL message, then video delivery continues. This corrects the original patch's assumption that every returned image is PNG; attached/editorial/upscaled images are not guaranteed to be PNG. MIME is reported metadata, not byte verification or a safety scan. No new URL policy, host permissions, credential forwarding, timeout, redirect rule or content-size guarantee is introduced; outbound media reads retain the existing authenticated callback's trust boundary. The shared downloader omits URL text from its non-2xx diagnostic; internal video log wording changes, not response bodies.

Callback validation uses the existing typed errorResponse constructor, preserving400 status, error/missing_fields fields and CORS. Existing secret validation runs before parsing/thread/media access. Callback idempotency remains its existing thread-state check; no concurrency-safe/exactly-once delivery claim is added. A callback with an image performs an additional media HTTP read and thread attachment/link post; generation count and charges are not increased by this source change. Existing buffering and Slack upload/runtime limits still apply. No new UI or workflow card is introduced.

Tests were written first. API regression tests exposed the stripped field, missing image posting/fallback and image filename handling; the new downloader suite initially could not load. Tasks tests exposed image loss in both polling results and actual callback JSON serialization. Final tests use mocked Trigger polling, fetch and thread leaves, actual schema/handler/poster/serializer code, and fixture secrets only. An initial red-only test lacked a default fetch stub and attempted a reserved example-domain media URL; that fixture was corrected and the retained red/green runs block all HTTP transport. No real service URL or credential was used. No real Slack post, worker run, generation, provider/customer/admin/database/key/credit operation or credential inspection was performed. Local/CI fixtures do not prove deployed worker results, hosted callback authorization, file rendering, quotas or delivery.

Both repositories use feature PRs with independent review. API-first release is the recommended sequence. Tasks main automatically deploys to Trigger.dev through its existing workflow, so its merge is an explicit worker-release boundary, not source-only housekeeping. No manual deploy or workflow activation is performed here. Docs owns the confirmed callback-field contract/publication companion; original438 remains untouched. Original651/SDKv7, hosted lipsync/provider/actor/commercial and other existing gates remain separate.
