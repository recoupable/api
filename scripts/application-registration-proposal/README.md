# Inactive application registration adapter

This inactive candidate binds proposed create/read calls to the existing nonprovisioning REST authentication path. It is not registered as a route or MCP tool and has no concrete database caller or production factory. The injected policy descriptor identifies an unadopted contract; it grants no authority. SQL personal enrollment and named entitlements remain required in the proposed storage boundary.

`node scripts/application-registration-proposal/run.mjs` executes the dedicated suite. The ordinary Vitest configuration deliberately excludes it. `.github/workflows/application-registration-proposal.yml` runs this command on every PR to main, including changes to any shared auth, validator, compiler or dependency input. CI checks the exact PR head with read-only permissions and no retained checkout credentials. A local pass is not a CI result.

The launcher creates a synthetic environment and temporary home, preloads network denial before Vitest/config/auth imports, disables Vite dotenv discovery and stops its owned process group before deleting temporary files. An uncertain process inventory preserves the directory and fails. Installed Vite 7.3.0 implements `envDir: false` by returning an empty dotenv filename list; the separately retained local qualification controls also used synthetic poison values in all four dotenv filenames and the ambient environment. Those poison controls are recorded in the sealed local review packet and are not injected by the ordinary CI launcher. Provider fetch, SDK verification, Supabase database access, Stripe and email are substituted leaves. Auth orchestration, API-key hashing/expiry handling, existing-account selection, evidence validation and canonical registration validation are real source calls. These tests do not establish provider cryptographic verification, hosted entitlement enforcement or authenticated deployed MCP acceptance. The accepted unregistered direct-SDK transport is described in [the MCP composition contract](../../docs/internal/mcp-existing-application-actor.md#inactive-direct-sdk-transport-composition).

## Transaction and recovery contract

Each invocation authenticates again and calls at most one storage method. Create calls contain the original verified actor and actor-owned workspace, canonical intent, supplied original idempotency key and safe expected revision; read calls contain the verified actor/workspace, environment and canonical application/receipt selection identifiers. No credential or client-supplied actor reaches storage. There is no retry ledger or automatic retry. If a call throws an unrecognized error or returns a malformed receipt, its outcome is unknown: retain the original operation, key and input. Only the injected storage contract can explicitly classify a denial or conflict; neither classification is inferred from an arbitrary error object.

Read input resource UUIDs accept uppercase aliases and are lowered after UUID validation, matching PostgreSQL UUID serialization. Returned receipt UUIDs must already use lowercase SQL serialization; neither returned identifiers nor actor authority are rewritten. Receipts must exactly bind actor/workspace/billing owner, environment, intent and selection identifiers. All five activation/persistence flags remain false. UTC timestamps keep the SQL text, including microseconds and `+00:00`; revisions must be safe JavaScript integers. Canonical arrays use UTF-8 byte order matching the UTF-8 SQL fixture's `COLLATE "C"` ordering. Invalid URLs are rejected instead of silently normalized.

## Authentication qualifications

The independent source review at API baseline 1fff6b55 identified boundaries retained here: Privy existing-account lookup still requires an external authenticated profile GET; `self` observes the absence of an override and does not prove personal enrollment. Existing REST API-key expiry rejects parseable elapsed timestamps but treats missing or malformed timestamps as non-expiring; the tests explicitly preserve that inherited behavior without adding a second verifier. Evidence contains no expiry epoch. Verification can race with credential revocation or profile/email remapping before the storage call; SQL does not receive a credential for atomic revalidation.

`executionResources` remains exactly unresolved. Guard-unit forged-evidence negatives establish structural rejection only, not cryptographic delegated-token rejection. Existing OAuth wrappers perform separate grant revalidation; that does not provide this adapter's original-actor evidence or personal enrollment. No MCP accountId/authInfo is adapted into an invented request credential. The separately owned OAuth expiry repair is included unchanged through the accepted merge. The legacy public MCP Privy fallback can still provision accounts. The separately accepted opt-in existing-account verifier and unregistered transport provide controlled original-actor handoff evidence, as described in the MCP composition contract; the public route is unchanged and no deployed handoff is claimed.
