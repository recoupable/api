# Inactive application registration adapter

This domain-only candidate binds proposed create/read calls to the existing nonprovisioning REST authentication path. It is not registered as a route or MCP tool and has no concrete database caller or production factory. The injected policy descriptor identifies an unadopted contract; it grants no authority. SQL personal enrollment and named entitlements remain required in the proposed storage boundary.

`node scripts/application-registration-proposal/run.mjs` executes the dedicated suite. The ordinary Vitest configuration deliberately excludes it. `.github/workflows/application-registration-proposal.yml` runs this command on every PR to main, including changes to any shared auth, validator, compiler or dependency input. CI checks the exact PR head with read-only permissions and no retained checkout credentials. A local pass is not a CI result.

The launcher creates a synthetic environment and temporary home, preloads network denial before Vitest/config/auth imports, disables Vite dotenv discovery and stops its owned process group before deleting temporary files. An uncertain process inventory preserves the directory and fails. Installed Vite 7.3.0 implements `envDir: false` by returning an empty dotenv filename list; qualification also used synthetic poison values in all four dotenv filenames and the ambient environment. Provider fetch, SDK verification, Supabase database access, Stripe and email are substituted leaves. Auth orchestration, API-key hashing/expiry handling, existing-account selection, evidence validation and canonical registration validation are real source calls. These tests do not establish cryptographic verification, hosted entitlement enforcement or real MCP authentication parity.

## Transaction and recovery contract

Each invocation authenticates again and calls at most one storage method. The call contains the original verified actor and actor-owned workspace, canonical intent, supplied original idempotency key and safe expected revision. No credential or client-supplied actor reaches storage. There is no retry ledger or automatic retry. If a call throws an unrecognized error or returns a malformed receipt, its outcome is unknown: retain the original operation, key and input. Only the injected storage contract can explicitly classify a denial or conflict; neither classification is inferred from an arbitrary error object.

Read input resource UUIDs accept uppercase aliases and are lowered after UUID validation, matching PostgreSQL UUID serialization. Returned receipt identifiers and actor authority are not rewritten. Receipts must exactly bind actor/workspace/billing owner, environment, intent and selection identifiers. All five activation/persistence flags remain false. UTC timestamps keep the SQL text, including microseconds and `+00:00`; revisions must be safe JavaScript integers. Canonical arrays use UTF-8 byte order matching the UTF-8 SQL fixture's `COLLATE "C"` ordering. Invalid URLs are rejected instead of silently normalized.

## SQL evidence and source pins

`source-bindings.json` records immutable API/SQL source heads and hashes. Before loading tests, the launcher recomputes every locally available `apiInputs` hash and the golden file hash and checks its database head. A mismatch fails qualification and requires a reviewed evidence refresh. External database source and local capture-driver/log hashes are provenance references verified in the sealed source-review packet; those external files are not present in this API checkout and are not reverified by API CI. `receipt-golden.json` contains actual create/read outputs from disposable PostgreSQL 15.10 with UTF8 encoding, using database proposal commit `df7be4c65b98924373b38c7d257f4b1c1820d6b7`. The capture used the proposal's existing supervised fixture runner, explicitly enrolled a synthetic UUID actor, granted create authority, invoked SQL create, explicitly granted named read authority and invoked SQL read. Create and read receipts were equal. The fixture reported worker group, postmaster and socket absence. No hosted database was contacted and no production migration or entitlement was applied. The capture driver and execution logs are retained in the coordinator's local audit packet; the golden file is synthetic evidence, not a receipt for a deployed application.

The original API baseline was `1fff6b55b8c1b98826c375f99b4f4f66a5ba201c`; this candidate now composes the accepted OAuth PR1268 merge `5605ee143afc4ebcdba9ba33dc7b48378c70a47f`. Its shared REST expiry resolver repairs the former MCP API-key expiry omission. That omission is historical after this source merge; it does not establish original-actor evidence, nonprovisioning Privy behavior or runtime acceptance. The fixture named “HTTP-shaped JSON and MCP-shaped argument” tests input projection only; fresh nonprovisioning MCP handoff remains unresolved. Database PR138 is a separate unmerged/unapplied proposal. All runtime activation and publication remain gated by coordinator review.

## Authentication qualifications

The independent source review at API baseline 1fff6b55 identified boundaries retained here: Privy existing-account lookup still requires an external authenticated profile GET; `self` observes the absence of an override and does not prove personal enrollment. Existing REST API-key expiry rejects parseable elapsed timestamps but treats missing or malformed timestamps as non-expiring; the tests explicitly preserve that inherited behavior without adding a second verifier. Evidence contains no expiry epoch. Verification can race with credential revocation or profile/email remapping before the storage call; SQL does not receive a credential for atomic revalidation.

`executionResources` remains exactly unresolved. Guard-unit forged-evidence negatives establish structural rejection only, not cryptographic delegated-token rejection. Existing OAuth wrappers perform separate grant revalidation; that does not provide this adapter's original-actor evidence or personal enrollment. No MCP accountId/authInfo is adapted into an invented request credential. The separately owned OAuth expiry repair is included unchanged through the accepted merge. The MCP Privy fallback can still provision accounts and the MCP handoff still does not supply this strict verifier-produced original-actor evidence.
